📋 整体业务流程

① 门店上报缺货→ ② 仓库采购入库→ ③ 自动判定已入库→ ④ 配送到店→ ⑤ 自动判定已完成→ ⑥ 90天未处理→自动关闭
  • 门店侧：各门店店员录入缺货商品和数量，提交后进入系统等待处理
  • 仓库侧：仓库采购到货入库后，系统把这批入库数量按各门店上报时间的先后依次抵扣还没满足的缺货需求：先报的先扣，扣够了的记录自动变为"已入库"。不做一对一的单据配对，也不区分这批货本来是为哪家店采购的。
  • 后台侧：管理员查看汇总、一键同步判定、标记状态、手动补录
  • 定时任务：每天凌晨 00:30 自动跑一次完整判定，无需人工干预

🟢 七种状态含义

🔴 待处理

门店刚上报，仓库还没采购或采购还没入库。需要仓库安排采购。

🔵 已订购

仓库已经向厂家下了采购订单，但货还没到。等入库后自动判定。

🟠 待付款

采购已下订单，但财务还没付款，通常不影响入库判定。

🟢 已入库

仓库采购入库累计量 ≥ 缺货需求量，系统自动标记。需要继续配送到店。

✅ 已完成

配送到门店的商品数量 ≥ 缺货需求量，系统自动升级。不再参与判定。

🟣 厂家断货

厂家通知此商品暂时无货，无法采购。管理员手动标记。一旦标记就是终态——不会被 90 天自动关闭，也不会被自动判定覆盖。

⚫ 已关闭

上报超过 90 天仍未处理，系统自动关闭，不再参与判定。

⚖️ 自动判定规则

核心逻辑：仓库采购入库 ≥ 缺货汇总（先报先得）

  • 数据源：从业务系统实时读取采购入库单（已审核）
  • 锚点规则：采购入库日期 不早于 缺货上报日期即算有效（当天入库也算）
  • 先报先得：同一商品多个门店上报时，按上报时间先后依次抵扣采购入库量
  • 多入口一套口径：定时任务 / 一键同步 / 行级「立即判定」按钮 → 全部用相同规则

配送口径升级（已入库 → 已完成）

  • 系统每天自动检查所有"已入库"记录的配送单（配送中心出库），如果该门店实际收到的配送量 ≥ 上报需求，自动升级为"已完成"
  • 已完成是终态，不再参与入库判定；需要再次上报新需求时重新提交

90 天自动关闭

  • 任何非终态上报，创建超过 90 天仍未处理（未入库、未订购、未付款），自动标记"已关闭"

30 天超时回退（已订购/待付款）

  • 变成「已订购」或「待付款」的记录，如果从改成那个状态的那天算起超过 30 天（不是上报日期）仍没到货、且仓库采购量还不够需求量，自动回退为"待处理"，备注"超时回退(30天未到货)"
  • 目的：订单下了超过一个月还没发货，一直挂着已订购状态会让仓库忽略它的存在。回退后回到待处理队列，让仓库重新关注或确认是否需要追单/取消
  • 每天凌晨 00:30 定时任务执行这条检查
💡 提示：超 30 天未配送的已入库记录不会自动回退——有可能被其他门店要走了。需要门店再次上报需求即可。

🔘 按钮功能速查

按钮 做什么 场景 改数据？ 通知？ 耗时 结果
🔄 一键同步 按仓库采购入库核对各门店缺货汇总，把已满足的从待处理改为已入库，同时检查配送单把已入库升级为已完成 平时发现状态不对、新入库后手动补跑；定时任务每天 00:30 自动跑一次 ✅ 改 ❌ 不发 30 秒到 3 分钟 完成判定的商品数量
📦 判定（行级） 只判当前这一个商品，核对仓库采购入库是否够它的缺货需求 单个商品刚入库、想快速确认它是否该已入库 ✅ 改 ❌ 不发 3 到 10 秒 判定结果弹窗
📬 发送到货通知 找出仓库已有货但门店还没收到通知的商品，推送一条到货通知到门店通知中心 采购刚入库、或想再发一轮配送提醒 ❌ 不改状态 ✅ 发系统内通知 10 到 30 秒 通知 X 条、跳过 Y 条
🚚 配送待办 列出所有已入库但门店还没配送到货的商品 安排配送、检查哪些已入库还没配 ❌ 只读 ❌ 不发 1 秒内 待配送商品清单弹窗
🔄 刷新订购数据 从服务器拉取最新数据：缺货上报表 + 采购计划（含实时库存、在途、供货商）；只读查询，不会跑入库判定，不会碰采购入库单 想看到最新的缺货上报、库存数字或供货商变化，但不需要跑判定时；一键同步刚跑完之后也会自动刷新一次 ❌ 只读 ❌ 不发 3 到 10 秒 页面数据刷新
✏️ 手动改状态 行内下拉框直接改单条上报的状态 自动判定有偏差时人工修正（例如厂家长期断货手动标） ✅ 改 ❌ 不发 1 秒内 状态立即更新
📋 批量标记 把勾选的所有商品统一改成目标状态 需要同时改多条记录的状态 ✅ 批量改 ❌ 不发 3 到 15 秒 X 条已更新

🔑 四个"刷新/同步"按钮的区别

  • 一键同步：改数据。跑完整自动判定（入库+配送升级），批量把该变状态的商品改掉。30 秒到 3 分钟。相当于"全量重算"。
  • 判定（行级）：改数据。只算当前这一个商品，速度快。3 到 10 秒。相当于"单点重算"。
  • 刷新订购数据：只读。拉取缺货上报表 + 采购计划（实时库存、在途、供货商），不跑入库判定、不碰采购入库单。3 到 10 秒。相当于"从数据库读最新快照，不改任何状态"。
  • 定时自动刷新：只读。页面每隔 N 秒自动拉一次最新数据（同"刷新订购数据"）。不触发自动判定。
简单记：想改状态用「一键同步/判定」；想刷新看数据用「刷新订购数据/自动刷新」。

📌 逐按钮详解（每按钮都写清楚九件事）

九个固定字段：① 在哪   ② 一句话作用   ③ 点下去系统走哪几步   ④ 该用的场景   ⑤ 别用的场景   ⑥ 改不改数据   ⑦ 推不推通知   ⑧ 耗时   ⑨ 结果在哪看   ⑩ 出问题怎么办   ⑪ 和相近按钮的区别

🔄 一键同步（工具栏左侧第一个按钮）

一句话：按仓库采购入库核对所有门店缺货汇总，批量改状态。

系统走哪几步：① 拉 SQL Server 所有采购入库单（BillType=34, InKRec=3）  ② 按商品聚合累计量  ③ 对每条未完结的上报（待处理/已订购/待付款），从最早上报时间开始 FIFO 依次消耗采购量  ④ 采购量够了→改「已入库」  ⑤ 查配送单，配送到店量≥需求→再升级「已完成」  ⑥ 已订购/待付款超 30 天没到货→回退「待处理」  ⑦ 非终态超 90 天→关「已关闭」  ⑧ 改完后触发升级到已配送的逻辑（查配送中心出库单）  ⑨ 最后自动刷新一次订购数据

该用：仓库刚采购完、状态明显不对、或每天早上例行检查。  别用：只想看最新数据（用刷新订购数据）、只想改一条（用行级判定）。

改数据：✅ 批量改状态   推通知：❌ 不推   耗时：30 秒 – 3 分钟

结果在哪看：弹窗显示"判定完成 X 条，升级为已配送 Y 条"，然后页面自动刷新。

出问题：长时间转圈没反应→网络断了；判定结果为 0 但明明有新入库→检查入库日期是否早于上报日期；没触发已配送→配送单还没生成。

和判定的区别：一键同步全量跑所有商品（30s-3min），判定只跑当前这一个（3-10s）。一键同步 = 全量重算，判定 = 单点修正。

🔍 判定（行级，每行右侧的小按钮）

在哪：列表里每一行的最右侧，「改状态」下拉框旁边。  一句话：只跑当前这一个商品的入库+配送判定。

系统走哪几步：① 拉这条上报的商品编码  ② 查 SQL Server 这个商品所有采购入库累计量   ③ 从这条的上报时间往后消耗入库量  ④ 够了→改「已入库」  ⑤ 再查配送单→够配送→升级「已配送」  ⑥ 返回判定结果弹窗

该用：知道某个商品刚入库想快速确认、一键同步太慢但只关心一个商品。  别用：想批量改、或列表里 20+ 条都要判（不如一键同步）。

改数据：✅ 改这一条   推通知：❌   耗时：3 – 10 秒

结果：弹窗直接显示判定结果（什么状态变了、用了多少入库量、还剩多少）。

和一键同步的区别：一键同步改所有商品（重+慢），判定只改这一条（轻+快）。行级判定不会跑 30 天回退/90 天关闭，那俩只在一键同步/定时任务里跑。

📬 发送到货通知（工具栏）

在哪：工具栏，「一键同步」右边。  一句话：找出仓库有货但门店还没收到通知的商品，推送系统内通知。

系统走哪几步：① 读所有非终态上报（排除已完成/已配送/厂家断货/已关闭）  ② 筛选出仓库库存 > 0 且门店还在缺货的  ③ 写 store_notifications 表（系统内通知，不是微信）  ④ 弹窗告诉用户发了几条、跳过几条。

该用：采购刚入库、想再发一轮配送提醒、门店反馈没收到通知。  别用：商品还没入库（发了也白发）。

改数据：❌ 不改任何状态   推通知：✅ 写系统内通知表   耗时：10 – 30 秒

结果：弹窗显示"通知 X 条、跳过 Y 条"；门店刷新页面点铃铛图标就能看到。

和一键同步的区别：一键同步改状态不发通知，这个发通知不改状态。两个互不干扰，可以先同步再发通知。

🚚 配送待办（工具栏）

一句话：列出所有已入库但门店还没配送到货的商品，方便安排配送。

系统走哪几步：① 拉所有「已入库」状态的上报  ② 查 SQL Server 配送中心出库单（vBuySendSumDetail，OutKRec='3'）  ③ 按商品+门店聚合已配数量  ④ 配≥需求→自动升级「已配送」+ 刷新角标  ⑤ 剩下的（已入库但配<需求）→弹窗列出。

该用：安排今天配送、检查哪些门店的货已经入库但没送到。  别用：只想看缺货汇总（用刷新订购数据）。

改数据：自动升级「已配送」  推通知：❌   耗时：1 秒内（弹窗秒开）

结果：弹窗里一张清单表，每行有商品、门店、需求、已配、还待配多少。

和一键同步的关系：一键同步会顺便升级已配送，但它主要目标是入库判定。配送待办反过来：主要目标是列清单，顺便做升级。两个都能升级已配送，一键同步升级更全（覆盖所有已入库记录）。

🔄 刷新订购数据（工具栏）

一句话：从服务器拉最新数据快照（缺货上报 + 实时库存 + 采购计划），只读不改。

系统走哪几步：① 读 Supabase reports 表（分页拉全量缺货上报）  ② 调 SQL Server usp_GetPurchasePlanWithFeedback 存储过程（实时库存、在途、供货商）  ③ 查配送中心出库明细  ④ 合并后返回前端 → 页面重绘。不碰采购入库单、不跑入库判定、不改任何状态。

该用：想看到最新的缺货/库存/供货商数字，但不需要跑判定时。一键同步刚跑完也会自动刷一次。  别用：想改状态（用一键同步/判定）。

改数据：❌ 只读   推通知：❌   耗时：3 – 10 秒

和一键同步的区别：一键同步 = 改数据（慢），刷新 = 只读快照（快）。刷新跟浏览器 F5 刷新的区别是：F5 会让浏览器重新加载 HTML/JS 缓存，这个只刷数据不重加载页面。

⏱️ 自动刷新间隔（工具栏下拉）

一句话：页面每隔 N 秒自动拉一次最新数据（跟「刷新订购数据」同样的只读接口）。

走哪几步：选间隔 → setInterval 定时触发 loadSummary() → 每次调 get_summary action。选"关"就 clearInterval。

该用：长时间开着后台监控（比如整天挂一个标签页）。  别用：临时查一下（手动刷新就行）。

改数据：❌ 只读   推通知：❌

注意：自动刷新跟「定时自动同步（00:30）」是两个东西。定时自动同步会改状态，自动刷新只读。

✏️ 行内改状态（每行右侧下拉框）

一句话：直接改单条上报的状态，绕过自动判定。

走哪几步：选目标状态 → 点保存 → 写 Supabase reports 表 → 页面重绘。

该用：自动判定有偏差时（比如厂家长期断货手动标「厂家断货」）。  别用：批量改（用批量标记）。

改数据：✅ 改这一条   推通知：❌   耗时：1 秒内

注意终态保护：「已配送/已完成/厂家断货/已关闭」这四个终态不能被手动改回——选了会提示"终态不可修改"。

📋 批量目标状态（批量操作区下拉框）

在哪：列表上方"批量操作"区域，和"批量标记"按钮在一起。  一句话：选批量标记要改成什么状态（待处理/已关闭/厂家断货/已配送）。

走哪几步：选状态 → 批量标记按钮变成可点   （单独选这个下拉框不改任何东西，只给批量标记做目标）。

改数据：❌ 选下拉本身不改，要点批量标记才改   推通知：❌

别选的坑：不能选中间态（已订购/待付款/已入库）做批量目标——批量标记是"直接改终态"，中间态靠自动判定流转。

✅ 批量标记（批量操作区按钮）

一句话：把勾选的所有商品统一改成目标状态。

走哪几步：① 收集选中行的 ID   ② 过滤掉终态（已配送/已完成/厂家断货/已关闭不能被批量改）  ③ 批量写 Supabase reports 表   ④ 弹窗显示 X 条已更新。

该用：需要同时改多条记录（比如一批都过期了统一标已关闭）。  别用：改单条（用行内改状态）；批量选已完成再改会被跳过。

改数据：✅ 批量改   推通知：❌   耗时：3 – 15 秒

和行级改状态的区别：行级一次改一条，批量一次改 N 条。批量会跳过终态，行级有终态保护提示。

❌ 清除选择（批量操作区按钮）

一句话：把所有勾选的 checkbox 清空。

走哪几步：clearSelection() → 所有行 checkbox.checked=false → 批量计数器归零。

改数据：❌ 不改   推通知：❌   耗时：1ms

和 Esc 键的区别：Esc 键也能取消选择，但点按钮更明确（不知道快捷键的新用户）。

⏱️ 回填操作时间（批量操作区按钮）

一句话：把勾选记录的 status_changed_at 统一改成当前时间 + 操作者。

走哪几步：收集选中行 ID → 批量 UPDATE status_changed_at/status_changed_by → 弹窗成功数。

该用：手动改了很多条但时间不对（之前是旧数据），想统一刷新时间戳。  别用：正常日常操作（自动状态变更会自己写时间）。

改数据：✅ 改时间戳字段   推通知：❌   耗时：1 – 5 秒

注意：只改时间戳，不改状态值。

🔍 状态筛选（工具栏下拉框）

一句话：按状态过滤列表——只看某一种状态的商品。

走哪几步：选状态 → loadSummary(keepFilters=true) → 重新拉数据 → 列表只剩筛选结果。

可选值：全部 / 待处理 / 已订购 / 待付款 / 已入库 / 已完成 / 已配送 / 厂家断货 / 已关闭。

改数据：❌ 不改   推通知：❌   耗时：3 – 10 秒（要重新拉数据）

和批量标记的交互：如果你把一条标记成「已关闭」而当前筛的是「待处理」，那条会从列表消失（正确行为）。切换下拉到「已关闭」就能看到。

🔧 手动同步（工具栏隐藏按钮 / 定时任务）

一句话：手动跑一次完整的定时任务（跟每天 00:30 自动跑的一模一样）。

该用：想重新刷新整个采购库存池（SPFXB_Result 过旧）、或需要补跑 30 天回退的逻辑。

💡 常见问题

Q: 当天入库算不算满足？为什么要专门用「立即判定」？

A: 算！采购入库日期不早于上报日期就算有效，当天入库完全算。但一键同步可能还没跑完当天新入库的批次，如果你知道某商品刚入库就想立刻确认，可以点行级的「判定」按钮单独跑。

Q: 状态显示「已入库」，但门店一直没收到货？

A: 这是正常的——「已入库」表示仓库采购已够，但还没配送到店。配送中心会自动升级为「已完成」（配送到店量 ≥ 需求）。你可以点「配送待办」看哪些已入库还没配，或在明细里看配送进度。

Q: 收到「已关闭」怎么办？

A: 这条上报超过 90 天没处理被系统自动关闭了。如果这个需求还存在，门店重新提交一条新的缺货上报即可，新上报不会受旧的影响。

Q: 门店没收到系统内通知？

A: 通知是仓库手动点「发送到货通知」才会推送的，不是入库自动发的。通知只发给「仓库有货但门店缺货」的上报。门店在页面上点通知中心（铃铛图标）查看。

Q: 同一个商品多家门店重复上报会不会互相影响？

A: 会互相消耗仓库的采购入库量——这是「先报先得」规则。同一商品多个门店都报了，仓库入库的那批货按上报时间先后分配：先报的先扣，扣够了的门店变已入库，剩下的继续等下一批入库。每家门店看到的是独立的上报记录。
